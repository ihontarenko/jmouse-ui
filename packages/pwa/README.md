# `@jmouse/pwa`

How a product becomes installable.

A **station** is one installable Progressive Web App: a surface set up for a single kind of work, with
only what that work needs. A product declares its stations; this package turns each one into a
manifest, links it from that station's own HTML entry, and — in later work — registers the single
service worker they share and offers them from a shelf.

Nothing in here knows what a product does. A station is a **task**, not a role, and which tasks exist
is the product's business. So is who may see one: the package takes a predicate and calls it.

## Two entries, and they must stay apart

| Entry | Runs in | For |
|---|---|---|
| `@jmouse/pwa` | the browser | the station contract, the manifest shape, and the checks over both |
| `@jmouse/pwa/vite` | Node, at build time | the plugin that emits manifests and links them |

The plugin must never pull React in behind it, which is why `PwaStation` (with its glyph) and
`StationDefinition` (without) are two types over one list of stations.

## Using it

```ts
// vite.config.ts
import { jmousePwa } from "@jmouse/pwa/vite"
import { stations } from "./src/stations"

export default defineConfig({
  plugins: [
    jmousePwa({
      stations,
      applicationName: "Innoventa",
      themeColor: "#1f2937",
      backgroundColor: "#ffffff",
      language: "en",
      icons: (station) => [
        { src: `/icons/${station.key}-192.png`, sizes: "192x192", type: "image/png", purpose: "any" },
        { src: `/icons/${station.key}-512.png`, sizes: "512x512", type: "image/png", purpose: "any" },
        { src: `/icons/${station.key}-512-maskable.png`, sizes: "512x512", type: "image/png", purpose: "maskable" },
      ],
    }),
  ],
  build: {
    rollupOptions: {
      input: {
        shell: "index.html",
        components: "station/components/index.html",
      },
    },
  },
})
```

Every station needs an **HTML entry of its own** in `rollupOptions.input`. The plugin derives the path
from `startPath` (`/station/components` → `station/components/index.html`) unless the station names an
`entry` itself, and writes the manifest beside it.

## ⚠️ The five things that fail silently

1. **`id` is set explicitly, to the station's key — never left to default.** It is what an installed
   application is keyed on, and it defaults to `start_url`. A manifest copied from another station
   installs *over* it rather than beside it, with no error anywhere.
2. **`scope` is the origin root for every station.** Narrowing it to the station's own path looks
   tidier and costs a service-worker registration, a cache and an update cycle per station. Sharing
   the scope is what makes several stations cheap on a phone.
3. **One HTML entry per station, and it cannot be consolidated.** A browser reads the manifest from the
   document it loaded, and changing `<link rel="manifest">` after navigation does not reliably re-arm
   the installation prompt — so one document offers exactly one installable identity. All the entries
   still share one bundle graph, so this is not duplication.
4. **`theme_color` cannot follow the live theme.** It is read at launch, out of a static file, before
   anything of the application runs. The `<meta name="theme-color">` tag the plugin injects *can* be
   rewritten at runtime and covers the browser chrome; the splash screen cannot be.
5. **A manifest with no icons is not installable**, and looks exactly like one that is. The build
   warns per station rather than refusing — an icon set that has not been built yet is an ordinary
   state of a half-finished product.

## The service worker

One worker, at the origin root, for every station at once — because stations share a scope and differ
only by manifest. It is **generated by the plugin** with the build's own asset list in it.

```ts
import { useWorkerUpdate } from "@jmouse/pwa"

const { updateAvailable, applyUpdate } = useWorkerUpdate()
```

The library detects; **the product renders the prompt**. Four strategies, and each is the one it is for
a reason:

| Request | Answered |
|---|---|
| a navigation | **network first**, cached copy only when offline — a cached document can no longer discover a new build |
| `/assets/…` (content-hashed) | **cache first** — the name changes when the bytes do, so a cached copy is never the wrong one |
| anything else same-origin | **stale-while-revalidate** — a manifest, an icon, a font out of `public/` is unhashed, so cache-first would pin the first copy forever |
| `/api/…`, cross-origin, non-GET | **not intercepted at all** |

`skipWaiting` is called only when the page asks, so a deploy cannot swap the worker out from under a
half-filled form. `unregisterStationWorkers()` ships from day one: a worker that needs devtools to
remove turns one bad deploy into a permanent one.

In development the plugin serves a **pass-through worker** that caches nothing, so registration and the
scope assertion behave the same locally without serving yesterday's module over a live edit.

## Installing

```tsx
import { InstallButton, useIsInstalled, useInstalledStation } from "@jmouse/pwa"

<InstallButton station={station} />
```

`beforeinstallprompt` is captured **at import time**, not in a component — it fires once, around first
paint, and a listener attached later is a listener attached too late.

`<InstallButton>` renders a control where one can work and a **sign where one cannot**: on iOS Safari
it prints the Share → Add to Home Screen instructions, and in any other iOS browser it says plainly
that nothing can be installed there. The capability is read from what the browser *does*, never from
its user agent string.

## Icons

```ts
paintIcons: {
  draw: (station, colours) => `<svg …>`,   // the same callback themedFaviconPainter takes
  colours: { plate: "#1f2937", ink: "#ffffff" },
  appleTouchIcon: (station) => `/icons/${station.key}-apple.png`,
}
```

Two files per station: the mark as the product drew it (`purpose: "any"`), and a maskable variant with
the glyph inset into the **80% safe circle** on a plate that bleeds to the edges. Android crops a
maskable icon to whatever shape its launcher uses, and only the middle 80% is promised.

⚠️ **`appleTouchIcon` must be a PNG the product supplies.** iOS ignores the manifest's `icons`
entirely; with no tag it puts a screenshot of the page on the home screen. Rasterising here would mean
carrying an image toolchain in a package that otherwise has no dependencies, so the build warns
instead.

## The shelf

```tsx
<StationShelf stations={stations} holds={authStore.holds} installedKeys={…} />
```

A station the predicate refuses is **not rendered at all** — not greyed, not disabled. A disabled tile
says both "this exists" and "you may not have it", which is a disclosure and an invitation to go and
ask; absence is the honest rendering of "this is not part of your work".

Opening performs a **real navigation** (`openStation`), never a router push. A client-side route to the
same address renders the right screen under the *wrong* manifest, which looks correct until somebody
tries to install it.

## ⚠️ Relative imports here carry a `.js` extension

Every sibling package's do not, and that is not drift. The others are only ever consumed through a
bundler, which resolves an extensionless specifier. `vite.config.ts` imports this one and Vite hands
that file to **Node**, which does not — without the extension the plugin entry throws
`ERR_MODULE_NOT_FOUND` for its own sibling module, at the moment a product first configures its build
and nowhere earlier.

## What is deliberately not here

- **Any station.** Those are the product's.
- **The offline write queue.** What a conflict means for a stock count is not what it means for a form
  entry, so it is per-domain rather than shared.
- **A second icon painter.** `@jmouse/ui` already owns `themedFaviconPainter`; the PWA icon set is
  that painter at more sizes plus a maskable safe zone.
